# Реализованный Slice 20: локальная MFA и аварийный доступ

Статус: реализован первый production-контур TOTP, server-side step-up,
двухэтапного восстановления учётной записи и ограниченного break-glass.
WebAuthn, независимый security review и физическое учение с реальными
хранителями доступа остаются отдельными обязательными gates.

## Локальная MFA и step-up

Пользователь подключает TOTP к собственной локальной учётной записи. Seed
создаётся CSPRNG, хранится только в PostgreSQL как AES-256-GCM ciphertext и
зашифрован отдельным 256-битным ключом `mfa_encryption_key`. Ключ не совпадает с
паролями PostgreSQL, node signing seed или ключом blob-хранилища.

Подключение требует текущий пароль. Замена уже активного TOTP дополнительно
требует действующий код. Старый фактор отключается только после успешной
проверки нового. Код принимается в окне ±30 секунд, но один и тот же moving
counter нельзя использовать повторно. Неудачные попытки имеют server-side
счётчик, временную блокировку и audit.

Успешная проверка создаёт в текущей server-side сессии step-up grant на 10
минут. Grant не переносится в access token и проверяется по БД при каждой
критической команде. Step-up требуется для управления ролями и сессиями,
security recovery, ключевых federation-команд, кризисных переходов, решений по
аномалиям и финализации клиринга. Финализация клиринга не допускает аварийного
обхода второго фактора.

## Восстановление доступа

Запрос создаёт сотрудник с постоянной контрольной ролью и активным step-up.
Он указывает пользователя, временный пароль, понятную причину и номер акта или
доказательства. Инициатор не может восстанавливать собственную запись.

Решение принимает другой уполномоченный сотрудник, который не является ни
инициатором, ни получателем доступа. При одобрении сервер:

- заменяет Argon2id-хеш пароля;
- требует сменить временный пароль при первом входе;
- отзывает все активные сессии пользователя;
- отключает его активный и незавершённый TOTP;
- сбрасывает локальную блокировку входа;
- создаёт подписанное событие и audit-запись без открытого пароля.

В idempotency registry сохраняется только HMAC-fingerprint временного пароля,
вычисленный отдельным MFA-ключом. Это позволяет отличить повтор команды с
другим секретом, не создавая в БД быстрый SHA-256 oracle для перебора пароля.

## Break-glass

Аварийное право выдаётся только из allowlist: `SECURITY_ADMIN`,
`NODE_SECURITY_ADMIN`, `NODE_TECHNICAL_CUSTODIAN`, `CRISIS_OPERATOR` и
`CRISIS_CONTROLLER`. Финализаторы клиринга в allowlist не входят. Заявка
содержит получателя, точный scope, роль, срок от 15 до 60 минут, причину и
доказательство. Решение требует другого человека; получатель и инициатор не
могут одобрить заявку.

Временная власть хранится в `identity.break_glass_grants`. Связанная
`RoleAssignment` с `source=BREAK_GLASS` служит только проверяемым основанием
для FK подписанного журнала. Обычная выдача ролей исключает такие записи, а
стандартные endpoints назначения и отзыва не могут изменить их lifecycle.
После истечения или отзыва роль немедленно исчезает даже из уже открытой
сессии. Каждое обращение пользователя с активным break-glass создаёт отдельную
`BREAK_GLASS_ACCESS_USED` запись с HTTP method/path и grant id.

Recovery и управление другими аварийными правами требуют постоянной личной
контрольной роли. Полученное временно право нельзя передать дальше или
превратить в постоянное через другой административный endpoint.

## События, данные и API

Revision `0025_identity_step_up` добавляет TOTP factors, step-up поля сессии,
recovery requests и break-glass grants. Revision
`0026_break_glass_authority` добавляет происхождение и срок полномочия в
`RoleAssignment`, сохраняя отдельный lifecycle и FK подписанного журнала. Revision
`0027_identity_index_alignment` приводит имя индекса фактора к metadata-модели без
пересоздания данных.

Подписываются события:

- `identity.account_recovery_requested`;
- `identity.account_recovery_executed` / `identity.account_recovery_rejected`;
- `identity.break_glass_requested`;
- `identity.break_glass_activated` / `identity.break_glass_rejected`;
- `identity.break_glass_revoked`.

API публикует `/api/v1/auth/security`, TOTP enrollment/confirmation/step-up и
отключение фактора, а также административные коллекции и команды
`/api/v1/admin/account-recoveries` и `/api/v1/admin/break-glass`.

## Интерфейс

Раздел **Безопасность** доступен каждому вошедшему пользователю. Он показывает
состояние второго фактора, step-up и активных аварийных прав. Подключение TOTP
имеет QR-код, ключ ручного ввода, три коротких шага и проверку шестизначного
кода. Уполномоченные сотрудники на том же экране видят recovery и break-glass,
но интерфейс не показывает инициатору кнопки собственного независимого
решения. Все новые надписи и ошибки покрыты русским и английским XML locale.

## Проверка и ограничения

Проверены AES-GCM round-trip/tamper, TOTP window/replay, обязательный step-up,
полный recovery, отзыв старых сессий и фактора, запрет самоодобрения,
активация/использование/отзыв break-glass, происхождение временной роли, пять
подписанных событий и их подписи. Миграции прошли populated cycle
`0024 -> 0025 -> 0026 -> 0027 -> 0026 -> 0025 -> 0024 -> 0027`.

Контрольный прогон: backend `177 passed, 1 deselected`; frontend `57` файлов и
`150 passed`; Ruff, strict mypy, typecheck и production build прошли локально.
Эти тесты не закрывают WebAuthn, независимый pentest, аппаратный
key storage, реальное учение восстановления и организационную проверку лиц.
