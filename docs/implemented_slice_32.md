# Slice 32. Сквозная прослеживаемость товарного исполнения

Статус: реализован и проверен code-level baseline. Для товарного исполнения
система сохраняет неизменяемую цепочку:

`партия -> товарное право -> завершённое погашение -> исполнение -> получатель`.

## Зачем это нужно

Факт доставки сам по себе не доказывает происхождение товара. До Slice 32
исполнение обязательства можно было связать с актами и логистикой, но нельзя
было одной проверкой установить, из какой партии возникло товарное право, кто
погасил его, кому предназначался товар и кто принял результат.

Теперь PRODUCT-исполнение невозможно создать без завершённого погашения
товарного права. Для услуги источник, напротив, запрещён: физическая партия к
ней неприменима.

## Инварианты

`ExchangeService.submit_fulfillment` проверяет в одной транзакции:

- партия, право, погашение и обязательство относятся к одному кооперативу;
- партия содержит именно товар обязательства и ту же единицу измерения;
- владелец права совпадает с должником;
- количество погашения, права и исполнения совпадает точно;
- право имеет статус `REDEEMED`, а погашение `COMPLETED`;
- событие погашения совпадает с событием погашенного права;
- погашение завершено не позже фактического исполнения;
- одно погашение связано только с одним исполнением.

Связь хранится в `exchange.fulfillment_provenance`. У неё нет операций
изменения или удаления через приложение, а уникальные ограничения по
`redemption_id` и `linked_event_id` дают вторую линию защиты от повторного
использования.

## Исторические записи

Для существовавшего до миграции исполнения предусмотрена отдельная команда
reconciliation. Она доступна только назначенным операторским ролям, требует
обоснование и готовое evidence, создаёт подписанное событие
`obligations.fulfillment_provenance_reconciled` и не изменяет исходное
исполнение. Автоматическое угадывание источника запрещено.

Downgrade миграции `0036_fulfillment_traceability` разрешён только для пустой
таблицы. При наличии истории он останавливается fail-closed.

## API и интерфейс

- `GET /api/v1/exchange/obligations/{id}/eligible-sources` показывает должнику
  только подходящие ещё не использованные погашения.
- `GET /api/v1/exchange/traceability` возвращает приватную цепочку с партией,
  правом, погашением, исполнением, логистикой, приёмкой, получателем и
  воспроизводимым `proof_hash`.
- форма исполнения требует выбрать источник для товара и не показывает этот
  выбор для услуги;
- панель трассировки доступна сторонам сделки, перевозчику и ответственным
  ролям, но не постороннему участнику.

## Демо и проверки

Детерминированный demo-сценарий создаёт доставку восьми килограммов капусты,
связывает её с погашенным правом на конкретную партию и фиксирует частичную
приёмку шести килограммов. Старое demo-исполнение проходит явное reconciliation
с отдельным актом.

`test_fulfillment_traceability.py` проверяет всю цепочку на реальном PostgreSQL,
точное количество, получателя, приёмку, запрет повторного использования
погашения, приватность API, формат доказательного SHA-256 и целостность
подписанного журнала.

Проверенный checkpoint 28 июля 2026 года: Ruff, strict mypy по `264` source
files, `252 passed, 1 deselected`; `69` frontend test files / `196` tests,
TypeScript typecheck и production PWA build. Живой узел имеет revision
`0036_fulfillment_traceability`, две provenance-записи и валидный журнал из
`434` событий.

## Остаточные границы

Техническая прослеживаемость не доказывает качество продукта без корректного
акта и не заменяет физическую инвентаризацию. Внешний аудит должен проверить
регламент reconciliation, полномочия операторов, сроки хранения evidence и
соответствие правилам конкретной юрисдикции.
