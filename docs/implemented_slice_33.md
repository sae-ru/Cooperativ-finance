# Slice 33. Exactly-once для хозяйственных активов

Статус: реализован и проверен code-level baseline. Критические операции выпуска,
погашения, резервирования и окончательного исполнения сериализуются в
PostgreSQL и имеют DB-backstop против повторного результата.

## Модель защиты

Exactly-once не опирается на один механизм. Каждая команда использует несколько
слоёв:

- обязательный `Idempotency-Key` связывается с типом команды, actor и payload;
- хозяйственная строка блокируется через `SELECT ... FOR UPDATE`;
- optimistic version отклоняет устаревшего конкурента;
- exact balance/state machine не допускает отрицательный или превышающий
  обеспечение результат;
- unique/check constraints не дают записать второй итог даже при ошибке сервиса;
- подписанное событие и audit создаются в той же транзакции, что и хозяйственное
  изменение.

## Выпуск и резервирование товарного права

Выпуск блокирует партию и `LotBalance`. Две конкурентные команды с одной
expected version пытаются выпустить по одной единице. Результат: одно право и
одна атомарно consumed reservation создаются успешно, вторая команда получает
`VERSION_CONFLICT`. Сумма `available + reserved + issued + quarantined`
остаётся равной backing с учётом shortfall.

Связь `CommodityRight.reservation_id` уникальна. Поэтому одна reservation не
может обеспечить два права.

## Погашение

Две конкурентные команды завершения одного `RightRedemption` блокируют
погашение, право, партию и баланс. Только первая переводит право в `REDEEMED`,
уменьшает физический остаток и создаёт одно движение. Вторая получает
`REDEMPTION_NOT_PENDING`.

Открытое погашение одного права дополнительно защищено partial unique index, а
событие движения уникально.

## Резервы других контуров

Конкурентные тесты дополнительно подтверждают:

- только одно risk commitment помещается в доступный незарезервированный
  остаток счёта;
- только одно solidarity allocation расходует проверенный остаток;
- только один crisis rationing plan подтверждает один snapshot;
- peer и inter-node receipts имеют уникальные ключи и повторяемые signed
  результаты.

## Execution

Две одновременные попытки принять одну финальную компенсацию дают один
`SETTLED` и один `RISK_VERSION_CONFLICT`. Единственная успешная транзакция
одновременно дебетует source, кредитует destination, освобождает
`executed_not_settled`, фиксирует before/after и закрывает liability.
Последующий повтор через API также отклоняется.

Клиринг отдельно проверяет две конкурентные финализации: создаётся один proof и
каждое обязательство получает clearing result один раз. Inter-node apply
защищён уникальным receipt и commit certificate.

## Остаточные границы

Гарантия действует для команд приложения и его runtime DB-role. Прямой доступ
привилегированного DBA, ручное отключение constraints или восстановление
несогласованной копии находятся вне этой границы и требуют разделения доступа,
подписанного restore-процесса и независимого аудита.
