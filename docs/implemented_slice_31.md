# Slice 31. Точная десятичная арифметика интерфейса

Статус: реализован инженерный baseline. Срез закрывает полный технический путь
хозяйственной величины от PostgreSQL до отображения в браузере без двоичной
арифметики с плавающей точкой.

## Назначение

Backend уже принимал и вычислял количество, оценку, цену, покрытие и паи через
Python `Decimal`, а PostgreSQL хранил их в `Numeric`. Frontend получал эти поля
как десятичные строки, но отдельные представления преобразовывали их в JavaScript
`Number` для сумм, сравнений и форматирования. На больших или дробных значениях
это могло незаметно изменить показанный остаток.

Slice 31 вводит общий модуль `frontend/src/shared/decimal.ts`. Он разбирает
десятичную строку в целый коэффициент `BigInt` и scale, а затем выполняет:

- сложение и вычитание;
- сравнение, минимум и проверку знака;
- каноническое строковое представление;
- округление только для показа;
- локализованное форматирование RU/EN без преобразования самой величины в float.

## Граница типов

Точные десятичные строки обязательны для количества, паёв, цены, стоимости,
оценённого ущерба, покрытия, резервов и остатков. JavaScript `Number` остаётся
разрешён для дискретных операционных параметров: количества событий, версии
политики, scale как целого метапараметра, TTL, часов, дней и глубины цепочки.

Серверный `float` допускается только для технического времени и метрик
производительности. Он не участвует в расчёте хозяйственных прав или
обязательств.

## Охват интерфейса

Общий decimal-контракт применён в клиринге, кабинете участника, обмене,
федеративном поиске и клиринге, риске и компенсациях, ответственности, правах,
солидарном и кризисном контурах. Суммы landed cost, доступных паёв, обязательств,
потерь, покрытий и распределений вычисляются до форматирования точно.

Старый кэшированный ответ без добавленного в Slice 30 поля `executed_amount`
читается как нулевое исполнение. Это сохраняет совместимость открытой вкладки при
обновлении frontend, не ослабляя актуальный OpenAPI-контракт.

## Проверки

Unit-тесты подтверждают:

- `0.1 + 0.2 = 0.3` без бинарной погрешности;
- перенос разряда на границе `Numeric(38, 12)`;
- сравнение значений больше `Number.MAX_SAFE_INTEGER`;
- отрицательные значения и экспоненциальную запись;
- локализованное RU/EN форматирование больших чисел;
- отклонение numeric wire-values, запятой, `NaN` и строк с посторонними единицами;
- статический запрет `Number(...)` и `parseFloat(...)` для известных бизнес-полей.

Проверенный checkpoint 28 июля 2026 года: `69` frontend test files, `196`
tests, TypeScript typecheck и production PWA build. Frontend-контейнер пересобран,
все пять сервисов Compose healthy. Живой browser smoke подтвердил RU/EN, desktop
и mobile `390x844` без горизонтального overflow, точные дробные остатки `29,5` и
`19,5`, а также отсутствие warning/error в консоли.

Изменения схемы данных, OpenAPI и миграция не требуются: wire-format остаётся
десятичной строкой, оба OpenAPI mirror имеют одинаковый SHA-256, а последняя
revision сохраняется `0035_bounded_compensation`.

## Остаточные границы

Точность расчёта не определяет юридическую цену пая и не заменяет утверждённое
правило оценки. Максимум знаков после запятой задаётся доменным API и схемой БД.
Отображение может округляться по правилам конкретного экрана, но доменная строка
и все промежуточные вычисления остаются точными.
