# Реализованный Slice 22: раздельный административный реестр

## Назначение

Slice 22 завершает базовый административный lifecycle идентификации. Интерфейс
и API больше не представляют «клиента» одной смешанной записью: организация,
участник хозяйственного обмена, его членство, учётная запись входа и технический
узел имеют отдельные реестры, статусы, полномочия и историю.

Удаление административных объектов через GUI не поддерживается. Приостановка,
выход и отключение выполняются явными переходами состояния, поэтому ссылки из
обязательств, паевых операций, аудита и подписанных событий сохраняются.

## Пять раздельных реестров

Рабочее место **Администрирование** содержит вкладки:

1. **Организации** — создание кооператива, приостановка и возобновление.
2. **Участники** — регистрация хозяйственного субъекта в доступной организации,
   поиск и проверяемый lifecycle участника.
3. **Членства** — самостоятельная связь участника с организацией, номер и
   переходы `PENDING`, `ACTIVE`, `SUSPENDED`, `ENDED`.
4. **Учётные записи** — отдельный login, необязательная связь с участником,
   создание, отключение и повторное разрешение входа.
5. **Узлы** — локальный узел и внешние узлы с переходом в полное рабочее место
   управления доверием, ответственностью и сертификатами.

Права не выдаются автоматически при создании Member или User. Назначение ролей,
MFA, сессии и аварийный доступ остаются отдельным контуром безопасности.

## Область видимости

Роль с `cooperative_id` видит только свою организацию, зарегистрированных ею
участников и её memberships. Глобальная роль с пустым scope видит весь локальный
реестр. Проверка выполняется на сервере для списков, overview и команд, а не
только скрытием элементов интерфейса.

Новый `Member` получает `registered_by_cooperative_id`. Revision
`0029_identity_registry_scope` добавляет внешний ключ, индекс и безопасно
заполняет поле первым по времени известным membership. Для старых записей без
истории допускается `NULL`, который интерфейс явно показывает как унаследованную
запись.

Для обратной совместимости `cooperative_id` в старом запросе создания участника
может отсутствовать только тогда, когда у регистратора ровно одна доступная
организация. При нуле или нескольких scope требуется явный выбор.

## Lifecycle и безопасность

Разрешённые переходы заданы доменной политикой:

- Cooperative: `ACTIVE <-> SUSPENDED`;
- Membership: `PENDING -> ACTIVE|SUSPENDED|ENDED`,
  `ACTIVE -> SUSPENDED|ENDED`, `SUSPENDED -> ACTIVE|ENDED`;
- User: `ACTIVE <-> DISABLED`.

Команда передаёт `expected_version`, причину и idempotency key. Недопустимый
переход или устаревшая версия отклоняются. Активация membership требует
активных участника и организации. Отключение User запрещено для собственной
текущей учётной записи и в той же транзакции отзывает все её активные сессии.
Критические переходы организации и учётной записи требуют постоянного
полномочия и свежего step-up.

## API

Добавлены команды:

```text
POST /api/v1/admin/cooperatives/{id}/transitions
POST /api/v1/admin/memberships/{id}/transitions
POST /api/v1/admin/users/{id}/transitions
```

Существующие list/create endpoints теперь применяют cooperative scope.
Ответы организации, участника и членства содержат необходимые timestamps,
registration scope, дату завершения и version для конкурентного изменения.
OpenAPI backend и frontend mirror синхронизированы; сохранена совместимость с
зафиксированным baseline.

## Проверки

- unit: допустимые и запрещённые переходы трёх lifecycle;
- PostgreSQL integration: создание и переходы всех сущностей, optimistic version,
  scoped lists/overview, запрет чужой организации и legacy single-scope request;
- security integration: отключение User немедленно отзывает выданную сессию,
  собственную активную учётную запись отключить нельзя;
- frontend: пять отдельных вкладок, создание организации, переход membership,
  отключение учётной записи и переход к управлению узлами;
- migration: `0028 -> 0029 -> 0028 -> 0029` и чистый `alembic check`;
- generated OpenAPI: 330 операций, exact frontend mirror, 0 несовместимостей.

Проверенный baseline Slice 22: Ruff, strict mypy по 239 source files, 194
обычных backend-теста, отдельный трёхузловой acceptance `1 passed`, 152
frontend-теста и production PWA build. Migration cycle и `alembic check` зелёные;
OpenAPI содержит 330 операций, exact frontend mirror и 0 несовместимостей.
Живой Docker-стенд работает на schema `0029`; RU/EN desktop/mobile smoke,
светлая и тёмная темы, отсутствие page overflow и browser errors проверены.
Браузерная проверка дополнительно устранила сырые `OPERATIONAL`/`dev` и вернула
доступные названия пяти иконкам вкладок на мобильном экране.

## Остаточные production gates

Slice не подменяет независимую проверку безопасности, утверждение юридических
процедур приостановки и выхода, реальное обучение административных ролей,
ручную accessibility/device matrix и пилотный аудит. Service clients, duplicate
merge procedure и массовый staging-import остаются отдельными последующими
срезами production readiness.
