# Реализованный Slice 23: безопасный ввод участников

## Назначение

Slice 23 закрывает риск массового или ошибочного создания участников. Ручная регистрация теперь сначала выполняет проверку дубликатов, а CSV-импорт проходит последовательность `staging -> dry run -> independent review -> apply`. Система не объединяет людей автоматически и не выдаёт импортированным записям роли, членства, паи, лимиты или учётные записи.

## Ручная регистрация

Перед созданием участника сервер проверяет в выбранной организации:

- точное совпадение хеша внешнего идентификатора;
- совпадение нормализованного имени с учётом регистра и повторяющихся пробелов.

Точное совпадение идентификатора блокирует создание. Совпадение имени требует явного подтверждения регистратора с кодом решения `DISTINCT_PERSON_CONFIRMED`. Кандидаты отображаются оператору, но silent merge не выполняется. Проверка и создание защищены общей advisory lock организации, поэтому параллельная регистрация не обходит контроль.

## Массовый импорт

Поддерживаются UTF-8 CSV с разделителями запятая, точка с запятой или табуляция. Максимальный размер файла составляет 1 МБ, максимальное число строк - 500. Разрешены только поля имени, типа идентификатора и значения идентификатора, включая документированные русские варианты заголовков. Неизвестные поля отклоняются, чтобы случайно не загрузить лишние персональные данные.

1. `MEMBER_REGISTRAR` загружает файл в staging.
2. Dry run валидирует строки и строит отчёт `READY`, `INVALID`, `DUPLICATE`.
3. Другой пользователь с постоянной ролью `DATA_STEWARD` утверждает или отклоняет пакет.
4. `MEMBER_REGISTRAR` применяет утверждённый пакет.
5. Непосредственно перед созданием сервер повторяет проверку под блокировкой организации. Если данные изменились после dry run, весь пакет отклоняется с `MEMBER_IMPORT_PREVIEW_STALE` без частичного создания.

Применяются только строки `READY`, порциями по 100 строк внутри одной транзакции. Ошибочная или дублирующая строка не создаёт участника. Исходный CSV и открытые значения идентификаторов в БД не сохраняются: остаются только SHA-256 безопасного представления источника и строки, а также хеш идентификатора.

## API

```text
POST /api/v1/admin/members/duplicate-check
GET  /api/v1/admin/imports
POST /api/v1/admin/imports
GET  /api/v1/admin/imports/{batch_id}/rows
POST /api/v1/admin/imports/{batch_id}/dry-run
POST /api/v1/admin/imports/{batch_id}/decision
POST /api/v1/admin/imports/{batch_id}/apply
```

Все списки и команды проверяют cooperative scope на сервере. Команды требуют `Idempotency-Key`, используют optimistic version и записываются в аудит. Создатель пакета не может сам утвердить его.

## Данные и миграция

Revision `0030_safe_member_intake` добавляет:

- `identity.member_import_batches` - состояние пакета, контрольные суммы, счётчики, создатель, независимый проверяющий и версии;
- `identity.member_import_rows` - безопасное представление строки, результат проверки, кандидат-дубликат и созданный участник.

Ограничения БД запрещают отрицательные или несогласованные счётчики и совпадение создателя с проверяющим.

## Интерфейс

В административном рабочем месте добавлена вкладка «Импорт». Она позволяет скачать шаблон, выбрать организацию, загрузить CSV, увидеть пакет и построчный отчёт, выполнить dry run, независимо утвердить или отклонить пакет и применить его. Ручная форма участника показывает найденных кандидатов и требует понятного подтверждения, если это другой человек с тем же именем. Все системные статусы, причины и ошибки локализованы на русский и английский.

## Проверки

Автоматические проверки покрывают парсинг локализованного CSV, ограничения размера и количества строк, запрет неизвестных полей, нормализацию имени, idempotency, независимое утверждение, повторную проверку перед применением, отсутствие частичного создания и явное решение при одинаковом имени. OpenAPI backend и frontend синхронизированы и совместимы с baseline.

Фактический результат checkpoint:

- backend без acceptance: `200 passed`;
- frontend Vitest: `164 passed`, покрытие statements `81.68%`, branches `70.19%`, functions `75.01%`, lines `87.77%`;
- трёхузловой federation acceptance: `1 passed`;
- Alembic downgrade/upgrade и `alembic check`: успешно;
- production-сборка frontend и Docker-образов: успешно;
- живой Docker-узел: `OPERATIONAL`, схема `0030_safe_member_intake`, база данных, файловое хранилище и ключ узла в состоянии `UP`;
- вкладка импорта проверена в русском и английском интерфейсе на desktop и mobile; горизонтального переполнения страницы и ошибок или предупреждений в консоли нет.

Vite сохраняет предупреждение о стартовом JavaScript chunk примерно `605 KB`; оно не блокирует сборку и вынесено в последующую оптимизацию загрузки.

## Оставшиеся production gates

Service-client lifecycle и управляемая процедура объединения подтверждённых дубликатов остаются отдельными срезами. Независимый security review, нагрузочные испытания на целевой инфраструктуре, обучение операторов и юридическое утверждение процедур не заменяются этой реализацией.
