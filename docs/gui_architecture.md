# Архитектура GUI

Статус: обязательная информационная архитектура production GUI.

## Принцип

GUI является рабочим местом по роли, а не универсальной витриной всех функций.
Он помогает человеку увидеть факты, последствия и ожидаемые действия, но не
заменяет серверную авторизацию и доменные проверки.

## Application shell

### Постоянная верхняя строка

- имя и статус локального узла;
- `NORMAL`, `DEGRADED`, `OFFLINE_EPOCH`, `CRISIS`;
- состояние локального API и последней синхронизации;
- активная организация и роль;
- число критических задач;
- меню сессии и step-up authentication.

Режим и состояние связи видны на каждом экране. Цвет дублируется значком и
текстом.

### Навигация

Левая навигация строится по роли. Пункт без полномочий не показывается, но это
не считается контролем доступа. Основные группы:

- Сегодня;
- Товары и склад;
- Сделки и обязательства;
- Паи и ответственность;
- Клиринг;
- Помощь и резервы;
- Споры и надёжность;
- Узел и синхронизация;
- Аудит и отчёты.

На мобильном используется нижняя навигация для 3-5 частых действий роли и меню
остального. Критические операции не прячутся за жестами без явной кнопки.

## Главный экран «Сегодня»

Показывает не декоративные KPI, а очередь работы:

- требуется моя подпись;
- ожидается независимая проверка;
- истекает срок обязательства, роли, ключа или резервирования;
- обнаружено расхождение;
- открыто окно спора или апелляции;
- sync package ожидает проверки;
- резерв пересёк порог;
- активная личная экспозиция пользователя.

Задача содержит объект, причину, срок, следующий безопасный шаг и риск
бездействия.

## Единая страница объекта

Партия, право, сделка, обязательство, поручительство, кампания и спор используют
один шаблон:

```text
Заголовок: тип, понятное имя, статус, версия
Ключевые факты: стороны, количество, место, срок
Доступные действия по роли
Вкладки:
  Обзор
  Связанные обязательства
  Ответственность
  Доказательства
  История
```

История является временной шкалой событий, а не сырым audit log. У каждого
события доступны подписанты, полномочия, доказательства и проверка подписи.

## Пошаговая критическая операция

1. Выбор предмета и цели.
2. Проверка доступного количества, лимита или пая.
3. Назначение исполнителя, принимающего и независимого проверяющего.
4. Добавление доказательств.
5. Preview последствий.
6. Подпись инициатора.
7. Ожидание независимого подтверждения.
8. Финализация сервером и выдача `event_id`.

Preview показывает неизменяемый summary hash, роль подписанта, максимальную
экспозицию, блокируемый контур пая, срок освобождения и следующий ответственный.

## Двойной контроль

Состояния операции отображаются явно:

`Подготовлено -> Подписано инициатором -> Ожидает контролёра -> Выполнено`

Один человек не видит кнопку второй подписи, если политика требует
независимость. Замена контролёра требует основания и сохраняется в истории.

## Паи и персональная ответственность

Экран разделяет:

- основной пай;
- защищённый остаток;
- гарантийный контур;
- ролевое обеспечение;
- инфраструктурный контур;
- активные и потенциальные экспозиции.

Каждая блокировка раскрывается до предмета риска, суммы, максимального убытка,
очереди покрытия, срока и решения об освобождении. Общий баланс без разбивки не
используется для подтверждения рискованного действия.

Цепочка ответственности показывается как последовательность людей и передач:
кто выполнил, кто проверил, кто принял сохранность, кто одобрил, кто отвечает
сейчас.

## Контекстная надёжность

Запрещён единый score. Интерфейс показывает матрицу контекстов, например
поставка, хранение, качество, логистика, поручительство, аудит. Для контекста
видны период, число событий, уверенность, исходные факты, ограничения и путь
реабилитации.

Пожертвование и размер пая рядом с надёжностью не отображаются.

## Солидарная помощь

Помощь визуально отделена от сделок и кредита. Для получателя не показывается
«долг», отрицательная позиция или обязанность повысить публичность. Оператор
видит минимально необходимые данные; публичный отчёт содержит агрегаты.

## Ролевые рабочие места

| Роль | Основной desktop flow | Основной mobile flow |
|---|---|---|
| Пайщик | обязательства, паи, предложения | подтверждение получения, QR |
| Кладовщик | партии, остатки, выдачи | приём, сканирование, передача |
| Контролёр | очередь независимых проверок | фото, измерение, attestation |
| Логист | маршруты и передачи | pickup/delivery/custody |
| Оператор | очередь процессов и исключений | срочные подтверждения |
| Клиринговый оператор | preview, disputes, finalize | только наблюдение/alert |
| Аудитор | журнал, доказательства, выборки | фиксация полевой проверки |
| Арбитр | case file, конфликт интересов | уведомления |
| Security admin | ключи, узлы, инциденты | срочный отзыв |

## Frontend state

- TanStack Query хранит server state и cache;
- локальный UI state не дублирует хозяйственные сущности;
- формы валидируются Zod, но сервер повторяет проверки;
- IndexedDB хранит shell, справочники, черновики и pending requests;
- черновик не получает `event_id` и всегда маркируется как непринятый;
- закрытые ключи и избыточная PII в браузере не хранятся;
- mutation после timeout проверяет idempotency result до повторной отправки.

## Ошибки и деградация

Ошибка содержит понятное действие: исправить поле, обновить объект, запросить
роль, открыть конфликт или обратиться к ответственному. Stack trace и
необработанный backend text не показываются.

При недоступности API GUI переключается в read-only cache и drafts. Он не
имитирует успешную хозяйственную операцию. После восстановления пользователь
просматривает каждый pending draft перед отправкой.
