# Реализованный Slice 21: полный версионированный антифрод-контур

## Назначение

Slice 21 расширяет объяснимую проверку аномалий до всех классов злоупотреблений,
перечисленных в разделе 24.5 ТЗ. Контур остаётся защитным: правило создаёт
`WARN` или временный `HOLD`, но не выносит обвинение, не списывает паи, не меняет
репутацию и не создаёт санкцию автоматически.

Инженерное покрытие не называется производственной калибровкой. Для каждого
правила есть положительный и отрицательный синтетический сценарий, однако
частота ложных срабатываний на реальном пилотном наборе пока не измерена.

## Версионированный манифест

Алгоритм `2.0.0` публикует неизменяемый для версии манифест:

- 13 классов риска;
- 15 правил, потому что манипуляция предложением и повторное использование
  обеспечения проверяются двумя независимыми правилами;
- версия каждого правила, тяжесть и реакция;
- перечень используемых доменных источников;
- версия синтетического набора `synthetic-v2.0.0`;
- SHA-256 канонического манифеста;
- `production_approved=false` и пустая pilot false-positive rate.

## Новые правила

Связанные участники определяются только по активным `RelatedPartyLink`.
Взаимная положительная оценка требует событий в обоих направлениях. Для
концентрации критического ресурса используется транзитивная компонента связей,
активный `ReserveTarget` и только положительный физический остаток проверенной
или замороженной партии.

Дробление лимита не ищет невозможное состояние сверх лимита: штатный сервис
риска уже запрещает его сохранить. Сигнал возникает при четырёх и более
однотипных обязательствах не больше 30% лимита каждое, если вместе они занимают
не меньше 80%. Это `WARN`, потому что такая структура может быть законной.

Синхронная репутация требует не менее трёх положительных событий от минимум
двух авторов в одном контексте за десять минут. Связь помощи и репутации требует,
чтобы именно подтвердивший взнос человек выставил донору положительную оценку в
течение 72 часов. Простая последовательность «взнос, затем любая оценка» не
считается достаточной.

Конфликт привилегированного решения проверяет предложения и утверждения фонда,
а также решение арбитра по связанному участнику. Дробление помощи требует трёх
пересекающихся кампаний одного оператора в одном фонде. Обход санкции требует
активной санкции, активной связи и создания второго member после начала санкции.

## Хранение и воспроизводимость

Revision `0028_antifraud_rule_manifest` добавляет к каждому
`risk.antifraud_scans`:

- `rule_manifest_hash` с SHA-256 CHECK;
- `calibration_dataset_version`;
- безопасный backfill старых запусков как нулевой legacy hash и `legacy-none`.

Новый запуск сохраняет `2.0.0`, точный хеш и версию набора в одной транзакции с
подписанным событием. Сигнал по-прежнему содержит код и версию правила,
неизменяемые наблюдавшиеся факты и пороги. Активный `MEMBER/HOLD` использует уже
существующий fail-closed enforcement в публикации предложения, расчёте доставки,
заказе и командах паевой экспозиции.

## API и интерфейс

`GET /api/v1/antifraud/rules` доступен ролям `RISK_ADMIN`, `AUDITOR` и
`SECURITY_ADMIN` по той же политике доступа, что и очередь сигналов. Ответ
содержит 13 классов, 15 правил, версию, хеш, синтетический scope и честный флаг
неподтверждённой производственной готовности.

Рабочее место **Проверка аномалий** показывает покрытие и понятные названия
рисков на русском или английском. Технические имена таблиц обычному оператору
не показываются. Отдельное предупреждение сообщает, что пилотная калибровка ещё
не выполнена. Детальный список раскрывается по запросу и показывает реакцию и
число инженерных сценариев.

## Проверки

- манифест содержит все 15 enum-кодов, уникален и имеет стабильный SHA-256;
- у каждого правила объявлены положительный и отрицательный сценарии;
- девять новых правил имеют парные unit-проверки порога и чистого примера;
- временные окна находят нарушающую подгруппу и не скрываются посторонней записью;
- PostgreSQL integration сохраняет version/hash/dataset, создаёт `HOLD`, реально
  блокирует команду и снимает удержание только после независимого решения;
- API возвращает 13/15, `SYNTHETIC_REGRESSION` и `production_approved=false`;
- RU/EN XML имеют одинаковый набор ключей, frontend component test проверяет
  предупреждение о пилотной калибровке;
- OpenAPI backend/frontend синхронизирован, TypeScript-типы сгенерированы;
- Ruff, strict mypy, обычный backend gate, frontend tests и production build
  входят в приёмку;
- migration gate выполняет `0027 -> 0028 -> 0027 -> 0028` и `alembic check`.

Проверенный baseline Slice 21: Ruff, strict mypy по 201 source files, 191 обычный
backend test, отдельный трёхузловой acceptance `1 passed`, 151 frontend test,
production PWA build, совместимый OpenAPI 327 operations с exact frontend mirror,
`alembic check`, populated rollback/forward и живой RU/EN light/dark
desktop/mobile audit без browser errors.

## Остаточные production gates

Slice 21 не закрывает:

- пилотный набор с размеченными реальными эпизодами и законными операциями;
- утверждённый допустимый false-positive rate по каждому правилу;
- проверку репрезентативности, drift и периодическую перекалибровку;
- privacy/legal review использования связей, санкций, помощи и репутации;
- независимый анализ сговора и adversarial обхода правил;
- утверждение порогов органами конкретного кооператива.

До закрытия этих пунктов `production_approved` остаётся `false`, а интерфейс не
имеет права скрывать это состояние.
